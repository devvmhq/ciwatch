description: Design one dex task for human approval, without changing any files.
argument-hint: <dex task id>
---

You are designing a change that a human will approve before anyone builds it.

The task, as dex JSON:

$task.output

Read AGENTS.md first, then the code the task touches. You can't edit files, and you shouldn't: this step only produces a design. When you look at recorded data (anything under `testdata/`, `.log` files), grep it or read only the lines you need; never read a recorded log whole.

**Guess at nothing open-ended in the first version.** If the task depends on guessing at input with no fixed format or rules (log formats, push histories, timing, what a human meant), design a first version that needs no guess: one that reports what it can know for certain, or asks the user with a flag. Propose the guessing part as a separate, optional follow-up task under "Follow-up tasks", for the human to accept or not.

Write the design in Markdown, short enough to read in two minutes, with these sections and these exact `##` headings for the second, third and fourth:

1. **What changes and why**, in a few sentences, in terms of the task.
2. `## Acceptance cases`: a numbered list of concrete cases the change must handle, each `AC-<n>:` followed by one input or situation and its exact expected result (output, exit code, file written). Each becomes at least one test. Keep it to the cases that define the task, usually three to eight. Together with the non-goals they mark the approved feature's path: the reviewer treats any defect a user can hit on that path as a major, named in an acceptance case or not, so think through the states a user can reach (interruptions, missing or vanished data, retries, partial failures) and cover the ones that matter.
3. `## Non-goals`: what this task deliberately doesn't do, including related inputs and cases a reviewer might expect. These are off the path: the reviewer puts them in the backlog, not in findings.
4. `## Inference`: `none`, or each place the behaviour rests on inferring something from timing or from a format ours to guess (log layouts, timestamps, the order of events, another tool's text), with what's inferred and what happens when the guess is wrong. A design with any inference always goes to the human for approval.
5. **Behaviour**: the commands, flags, output and exit codes a user will see, with one concrete example.
6. **Code**: the files and functions you'd add or change, and any new dependency (avoid new dependencies unless the task needs one).
7. **Tests**: the tests to write first, each naming the acceptance case it covers, with what it feeds in and what it expects. They must fail before the change and pass after it. Golden files and fixtures are recorded from real output, or written by hand from it, never generated by running the code under test.
8. **Follow-up tasks** (only if needed): each proposed task's name and a one-paragraph description, ready to become a dex task if the human agrees.
9. **Questions**: anything ambiguous in the task, with the answer you'd assume.

Reply with the design only.
